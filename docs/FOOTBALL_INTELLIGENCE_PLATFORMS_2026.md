## 一、执行摘要与顶层愿景

### 1.1 足球数据智能平台演化简史与 2026 行业拐点
世界足球数字化在过去二十年间经历了三次重要变化：
1. **第一浪潮：门户与基础比分时代（2000–2012）**：以 Flashscore、BBC Sport、早期门户为代表，核心解决“快讯与基础统计传递”，用户消费的数据局限于比分、进球者、黄红牌与粗糙的射门/控球百分比；
2. **第二浪潮：事件建模与空间可视化时代（2013–2022）**：Opta F24 编码与 StatsBomb 开源协议推动了现代足球数据科学的建立，Expected Goals (xG)、Expected Assists (xA)、核密度触球热力图（Heatmap）和传球网络图（Pass Networks）进入大众视野。Sofascore 与 FotMob 凭借工业级流畅的移动 App 成为全球数十亿球迷的必备看板；
3. **第三浪潮：战术因果推理与人机协作交互智能时代（2023–2026+）**：大语言模型（LLM）与生成式人工智能爆发，行业开始探索自动化战报与自然语言战术查询。

然而，站在 2026 年的行业节点，足球数字化生态却陷入了显著的**“繁荣中停滞”**。

### 1.2 传统比分平台 vs 新兴 AI 平台的双重行业价值断层
通过对全球 10 余款标杆产品的独立穿透式调研，我们确诊了当前数字足球生态的两大核心断层：

```
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                                现代数字足球生态的双重价值断层                                    │
├─────────────────────────────────────────────────┬────────────────────────────────────────────────┤
│ 1. 传统即时比分平台的“数据密集但因果割裂”        │ 2. 新兴 AI 足球产品的“套词同质化与事实幻觉”   │
├─────────────────────────────────────────────────┼────────────────────────────────────────────────┤
│ • 堆砌了海量指标（控球率65%, 射门18次, 评分7.8）│ • 通用大模型缺乏足球数据约束，充斥空洞套话     │
│ • 数据彼此孤立，无法解释“为什么发生”            │ • 缺乏微观事件与空间坐标锚定，事实核验不足    │
│ • 用户看到动量暴跌，却不知是哪次防线被击穿      │ • 盲目臆测无球防守阵型，给出数据无法支持的确定结论│
│ • 交互单向被动，图表静态不可穿透                │ • 纯单向文本输出，缺乏可反驳、可交互的验证闭环 │
└─────────────────────────────────────────────────┴────────────────────────────────────────────────┘
```

### 1.3 MatchLens 的破局使命与核心设计哲学
**MatchLens 2026 的终极使命**：打破传统比分网的“数据离散冷冰”与新兴 AI 的“套词幻觉漂浮”，探索构建**“以微观事件数据为底盘、以空间几何大画布为骨架、以可溯源、分层标注的多智能体证据分析为中枢”的交互式足球战术智能平台**。

其核心贯彻四大不可妥协的设计哲学：
1. **Evidence-First（证据先行）**：不存在无证据的主张。AI 提出的每一条战术论断，必须强类型绑定底层事件槽位（Event IDs, Player, Coordinates, Sequences）；
2. **Click-to-Inspect（点击即验证）**：UI 上的每一个结论、波浪图上的每一个波峰、报告里的每一句论述，均支持一键下钻穿透，在球场画布上动态回放真实轨迹；
3. **Truth over Illusion（恪守数据边界，反伪科学）**：严格坚守数据分水岭。在仅有轻量事件数据时，绝不伪造全场 22 人无球防守阵型，而是主动触发“无球盲区置信度降级机制”，以诚实建立无可撼动的专业学术公信力；
4. **Adversarial & Reversible（对抗可辩驳）**：提供“战术假设实验室”与“用户质疑仲裁”，允许球迷与分析师对 AI 结论发起对抗性驳斥，形成人机协同的战术认知演化闭环。

### 2.2 比赛中心 (Match Center) 核心功能全景与微交互剖析

比赛中心是所有足球产品争夺用户停留时长的核心战场。现代成熟比赛中心包含六大核心战术组件：

#### 2.2.1 实时比分板与比赛状态 (Live Scoreboard & Status)
- **状态表达**：精确展示当前比赛分钟数（如 `45+2'`、`88'`），配合脉冲呼吸灯（Pulse Glow）提示实时数据连通；包含 VAR 介入提示（`VAR Review: Possible Penalty`）；
- **微交互反馈**：进球瞬间触发比分卡片翻牌动画与振动反馈（Haptic Feedback），伴随全屏半透明主队色系微闪。

#### 2.2.2 攻防动量曲线 (Attack Momentum) 与 MatchLens Observed Attacking Activity Index

- **竞品公开信息**：Sofascore 官方介绍说明其动量图使用进攻推进、射门、定位球等输入，但**并未披露完整公式、系数与平滑方案**。本报告不声称还原了 Sofascore 的算法，下文是 MatchLens **自主定义**的指标。
- **视觉形态（观察自竞品）**：横轴为比赛时间，上侧为主队活动优势，下侧为客队活动优势，叠加进球、红黄牌、换人、VAR 等事件标记。
- **MatchLens 自定义指标：Observed Attacking Activity Index（OAAI）**。它度量“已记录事件反映的进攻活动强度”，**不是**对比赛“势头”或心理动量的因果度量。设计分为三层，彼此独立可测：

| 层 | 职责 | 设计要点 | 待验证项 |
| :--- | :--- | :--- | :--- |
| **L-A 事件贡献层** | 为每个事件赋予一个有符号贡献 $c_k$ | 贡献表由明确公式给出：推进类事件取 $\Delta xT$ 或区域权重，射门取其 xG（xG 模型须按 `XT_MODELING_SPEC.md` 同类协议记录来源与校准）；权重表作为版本化配置文件，不硬编码 | 权重敏感性分析；不同事件类型贡献的量纲一致性 |
| **L-B 时间聚合层** | 将 $c_k$ 聚合到时间轴 | 仅使用时刻 $\le t$ 的事件（因果滤波），窗口长度、衰减核与“有效比赛时间”定义均为超参数；死球 / VAR / 伤停区间是否冻结衰减，须由实验决定并记录 | 无未来信息泄漏的单元测试；死球、低事件密度、不同时长比赛下的行为 |
| **L-C 可视化平滑层** | 仅用于显示 | 平滑核只影响绘图，不得反向进入指标或 Agent 证据；实时模式用单边核，赛后回放可选用双边核，并在界面标明 | 两种模式差异的可视化对照 |

- **实时可用性约束**：L-B 必须保证 $\text{OAAI}(t)$ 只依赖 $t$ 之前已发生的事件。赛后双边平滑生成的曲线不得标注为“实时”。
- **解释边界**：曲线的拐点只能表述为“该窗口内记录到的进攻活动贡献发生变化”，并可列出贡献最大的若干事件（见第 4.2 节 Level 2 指标归因）；不能直接表述为“某战术动作导致势头逆转”。
- **评测计划**：在多场样本上检验 (a) 与后续窗口内射门 / xG 的相关性（Level 3 统计关联）；(b) 与竞品公开曲线的主观一致性仅作定性参考；(c) 参数扰动下拐点位置的稳定性。具体数值结论须由实际运行产出，本文不预设。

#### 2.2.3 射门分布图与门框期望进球 (Shot Map & xGOT)
- **俯视 2D 射门图**：俯视进攻半场，散点大小映射该次射门的**期望进球值 ($xG \in (0, 1)$)**，颜色区分进球（绿）、射正（实心圆）、射偏（空心圈）、封堵（灰色）；
- **球门截面进阶指标 xGOT (Expected Goals on Target)**：
  - xG 评估的是**球离开射门者脚部瞬间的概率**；
  - xGOT 评估的是**射门越过门线/到达门框平面时的飞行质量与扑救难度**；
  - 配套“球门截面面对视角 (Goal Mouth View)”：当射门飞向球门死角时，$xGOT \gg xG$，反映球员完成了高质量终结；若射门绵软居中，$xGOT < xG$。两者之差量化了球员在门前的**终结净增益 (Shooting Added Value)**。

#### 2.2.4 传球网络与阵型拓扑 (Pass Networks)
- **节点 (Node)**：每个首发球员在场上的**触球平均中心坐标 (Median Centroid Position)**，圆圈大小映射球员全场总触球量；
- **连线 (Edge)**：两名球员之间成功传球次数（通常设定 $\ge 3$ 或 $\ge 5$ 次显示连线），线条粗细映射连线传球频次；
- **战术洞察**：一眼识破球队名义上的“4-3-3”在实战中是否异化为“3-2-4-1”，识别出后场出球中枢以及哪一侧边路陷入战术孤立。

#### 2.2.5 触球热力图 (Touch Heatmap)
- **核密度估计 (KDE)**：基于高斯核将离散的触球 $(x, y)$ 坐标平滑为连续的热度场，用于反映球员在全场的活动走廊；
- **战术九宫格/18区离散切分**：更专业的产品采用战术网格切分，量化在左半空间 (Left Half-space)、禁区弧顶与边路走廊的触球频次与成功率。

#### 2.2.6 球员评分与对比雷达 (Player Ratings & Radar)
- **算法评级机制**：以 6.0 分为基础分，成功传球、关键传球、过人、抢断、射门加分；失误、被过、失单刀、红黄牌、乌龙扣分；
- **全场 MVP 机制**：评分最高者标注金色皇冠；辅以 6 轴能力雷达图（进攻、创造力、传球、对抗、防守、体能）展示球员风格。

### 2.4 控球序列、xT 期望威胁马尔可夫网格与 OBV 双向净胜球增值模型

#### 2.4.1 控球序列模型 (Possession Sequences & Chains)
足球比赛不是离散事件的杂乱拼接，而是由一系列**有目的、连续的控球序列 (Possession Sequences)** 构成的因果流：
1. **序列切分准则**：
   - **开始条件**：从本方控球开始（拦截夺回、对方传球失误接球、门将开球、定位球发球）；
   - **延续条件**：本方球员之间的连续传球、盘带推进、对抗护球；对方球员的被动触碰但未改变球权；
   - **终止条件**：球权被对方有效控制、出界、犯规违例鸣哨、射门发生。
2. **核心指标公式**：
   - **直接推进速度 (Direct Speed)**：
     $$\text{Direct Speed} = \frac{\Delta x_{\text{progression}}}{\Delta t_{\text{duration}}} \quad (\text{m/s})$$
     高 Direct Speed（$>3.5\text{ m/s}$）代表高效犀利的反击；低 Direct Speed（$<1.5\text{ m/s}$）代表低速阵地倒脚。
   - **净推进米数 (Net Progression Meters)**：整条序列从起点至终点的纵向净位移。

#### 2.4.2 xT (Expected Threat) 网格马尔可夫模型
Karun Singh 提出的 xT 模型彻底量化了**非射门动作（传球、盘带）为球队带来的进球概率增益**：
将球场划分为 $16 \times 12$ 或 $12 \times 8$ 的离散网格，对于网格单元 $(x, y)$，其期望威胁价值满足马尔可夫转移稳态方程：
$$xT_{(x,y)} = s_{(x,y)} \times g_{(x,y)} + m_{(x,y)} \times \sum_{x',y'} T_{(x,y) \to (x',y')} \times xT_{(x',y')}$$
- $s_{(x,y)}$：在该网格选择直接射门的概率；
- $g_{(x,y)}$：在该网格射门的进球转化率；
- $m_{(x,y)}$：选择传球或盘带移动的概率（$m = 1 - s$）；
- $T_{(x,y) \to (x',y')}$：从该网格移动到下一网格 $(x', y')$ 的转移概率矩阵。
当球员完成一次从 $(x_1, y_1)$ 到 $(x_2, y_2)$ 的传球时，其创造的**净推进威胁值**为：
$$\Delta xT = xT_{(x_2, y_2)} - xT_{(x_1, y_1)}$$

#### 2.4.3 OBV (On-Ball Value / 控球增值模型)
区别于 xT 仅奖励向前进攻，StatsBomb 旗舰模型 OBV 建立了**全场双向攻防价值度量**：
$$\text{OBV}(\text{Action}) = \Delta P(\text{Goal For in } \tau) - \Delta P(\text{Goal Against in } \tau)$$
它既能奖励一次阻止绝杀的后场大脚解围（大幅压低失球概率），也能惩罚前场无脑浪射与失误粘球，是真正的全时段全动作价值量化体系。

### 2.5 事件数据与无球状态的可辨识性边界 (Identifiability Boundary)

产品架构中一个常见误区，是试图仅凭离散事件数据在球场上渲染 22 名球员的无球防守阵型。本节用**可辨识性分析**说明这种做法为何无法给出确定结论，同时避免把它夸大为“完全不能做概率估计”。

> **修订说明**：本报告早期版本使用“奈奎斯特采样定理 + 40 维零空间”的“严格不可能定理”。该论证不成立：事件并非对全体球员位置的定频采样，观测映射的线性性与秩也未建立，2 Hz 带宽属于未经验证的假设。已整体替换为下述论证。

#### 2.5.1 问题形式化
设时刻 $t$ 全体球员的真实位置状态为 $S_t$，数据提供方记录的事件观测为 $E_t = h(S_t)$（$h$ 一般只包含持球者位置、动作类型、结果、少量对手位置等字段）。

**可辨识性判据**：若存在两个不同状态 $S_t^{(1)} \neq S_t^{(2)}$，满足
$$h\big(S_t^{(1)}\big) = h\big(S_t^{(2)}\big),$$
则仅凭该时刻的事件观测无法唯一识别真实状态。

#### 2.5.2 构造性反例
取同一条事件记录：“某球员在 $(x_0, y_0)$ 完成一次向前传球，终点 $(x_1, y_1)$，结果为成功”。
- 状态 $S^{(1)}$：防守方四名后卫组成紧凑低位防线，防线高度较低；
- 状态 $S^{(2)}$：防守方整体高位压迫，防线高度较高，边后卫已前提；
- 两个状态都与上述事件记录相容，但防线站位、球员间距、越位线位置均不同。

因此 $h$ 不是单射。**“真实阵型无法由该事件唯一确定”这一结论成立**。

#### 2.5.3 结论的适用范围与不过度推广
1. **成立的结论**：仅凭常规事件数据，不能把“防线高度、紧凑度、无球跑位”当作已观察的事实输出。
2. **不成立的推广**：这不等于“完全无法做任何概率估计”。例如可在明确假设下用多场数据学习“球队倾向的防线高度分布”，并给出带不确定区间的先验估计；这类输出必须标注为 Level 3 或 Level 4 的模型推断（见第 4.2 节），而不是观察事实。
3. **StatsBomb 360 等冻结帧数据**：在事件发生瞬间提供画面内可见球员位置，缩小了不可辨识空间，但仍不是连续全场追踪，且受相机视野限制，使用时同样需要覆盖率说明。
4. **产品规则**：当用户追问无球防守站位时，系统应触发 Data Sufficiency 提示，说明当前数据能回答与不能回答的部分，并提供可观察的替代指标（如压迫类事件、失去球权后一段时间内的再夺回现象等）。该能力在 R2 已有 Evidence Gap Advisor 基础，见第 5.3 节分类。

### 2.6 新兴 AI 足球产品前沿探索 (TacticAI 等) 与行业四大致命痛点深度诊断

#### 2.6.1 前沿技术代表：Google DeepMind TacticAI
- **研究内容**：DeepMind 与利物浦足球俱乐部合作，针对**角球**场景使用几何深度学习（图神经网络）建模，任务包括接球人预测、射门预测与战术站位调整建议；
- **评估结论的正确表述**：论文报告中，专业评审人员在盲评比较中，**在相当比例的案例里更偏好模型给出的角球战术建议**（论文摘要给出约 90% 的偏好比例）。这是“专家在特定角球建议比较中的偏好”，**不代表“90% 的实战战术取得成功”**，也不能推广到非角球场景；
- **产品启示**：高价值 AI 往往聚焦于**结构化数据、闭环场景和专家评估**，而不是开放式闲聊。该系统依赖追踪位置数据，与仅有事件数据的产品并非同一数据条件。

#### 2.6.2 现有 AI 足球产品的四大致命痛点
1. **痛点 1（文本同质化与空洞废话）**：
   大量套壳大语言模型（LLM）足球助手由于缺乏底层精确足球数据与专业战术提示词编排，输出内容充斥着“双方展开激烈争夺”、“展现了顽强的拼搏精神”等老旧套话，味同嚼蜡；
2. **痛点 2（事实与数字严重幻觉）**：
   通用模型在没有结构化数据管道绑定时，极易编造虚假的助攻者、幻造未发生的角球甚至篡改比赛时间；
3. **痛点 3（缺乏技战术因果与空间证据）**：
   只能描述宏观结果（“客队赢了”），无法解释深层战术胜负手（“客队通过针对对手左后卫内收后的肋部真空，在 15 分钟内连续打出 4 次直接推进”）；
4. **痛点 4（单向不可验证黑盒）**：
   用户只能被动阅读生成的静态文本，无法点击交互，无法校验背后的数据来源与逻辑推导，导致专业用户弃用。

### 3.2 数据架构：三个正交维度与四类隔离对象

> **修订说明**：早期版本使用 L1–L12 线性“金字塔”。该表示适合科普，但不适合作为技术架构：数据并不严格按 L1→L12 依次依赖（例如 xG 可由事件与射门特征建模，360 是事件瞬间的冻结帧，阵容元数据与模型估计属于不同维度）。正式规划改为下列三个正交维度。

#### 3.2.1 三个正交维度

| 维度 | 内容 | 核心问题 |
| :--- | :--- | :--- |
| **Data Coverage（数据覆盖）** | 比赛元数据、阵容、事件、空间坐标、360 冻结帧、Tracking、视频 | 实际观察到了什么？ |
| **Derived Analytics（衍生分析）** | 控球序列、进攻推进、xG、xT、球员贡献、OAAI | 能计算或估计什么？ |
| **Evidence Quality（证据质量）** | 数据完整性、来源、模型校准、不确定性、许可与署名 | 结果可信到什么程度？ |

每个功能都应在三个维度上各登记一次：需要什么覆盖、产出什么衍生量、证据质量如何。

#### 3.2.2 四类互相隔离的工程对象

```
RawSourceRecord  ->  NormalizedEvent  ->  DerivedMetric  ->  VerifiedClaim
 (原始来源记录)       (规范化事件)         (衍生指标)          (已核验论断)
```

| 对象 | 含义 | 隔离规则 |
| :--- | :--- | :--- |
| `RawSourceRecord` | 数据提供方的原始记录、来源事件 ID、Schema 版本、许可信息 | 只读；不做任何推断 |
| `NormalizedEvent` | 统一 Schema 下的事件，只含**已观察**字段 | 不得混入模型输出 |
| `DerivedMetric` | xG、xT、OAAI 等，带模型版本、训练数据与不确定性 | 缺失值与真实 0 必须可区分（见 6.3 节） |
| `VerifiedClaim` | 经 Verifier 与门禁核验、带 `claim_level` 的论断 | 只引用 `NormalizedEvent` 与 `DerivedMetric` 的 ID |

#### 3.2.3 数据覆盖等级（用于功能可行性登记）

| 覆盖等级 | 典型来源 | 可支撑的功能类型 | 主要风险 |
| :--- | :--- | :--- | :--- |
| C0 合成数据 | 内置情节生成器 | 产品演示、回归测试 | 不代表真实足球分布，不得用于模型训练结论 |
| C1 开放事件数据 | StatsBomb Open Data 等 | 序列、热区、传球网络、xG/xT 训练、单场与多场分析 | 赛事覆盖有限；需遵守署名与使用条款 |
| C2 事件 + 360 冻结帧 | 部分开放 / 商业数据 | 事件瞬间的可见球员位置分析 | 视野外球员缺失，覆盖率因事件而异 |
| C3 授权实时事件 | 商业 API | 实时比分与事件推送 | 授权成本与条款，须逐家核实 |
| C4 Tracking | 商业光学追踪 | 跑动、压迫、控制空间等 | 许可严格、成本高，当前不在范围内 |
| C5 视频 | 转播或授权素材 | 视频与事件同步 | 版权限制 |

### 3.3 功能可行性分级（数据条件 × 建模条件）

### 4.2 核心方向：四层足球推理体系与重写后的创新方向

#### 4.2.0 Evidence & Causal Claim Framework（四层推理体系）

早期版本把“事件先后关系”“指标贡献”和“战术因果”混为一谈（例如用 5–15 秒的事件回溯直接宣称因果拓扑）。正式框架将每条论断明确分层：

| 层级 | 名称 | 含义 | 示例 | 验证方式 |
| :--- | :--- | :--- | :--- | :--- |
| **Level 1** | Observable Facts（可观察事实） | 可从原始事件直接计算，确定性 | 第 35 分钟记录到球权夺回，8 秒后发生射门 | 事件 ID 引用 + 重新计算 |
| **Level 2** | Metric Attribution（指标归因） | 由明确公式计算的指标贡献，**不等于**真实战术因果 | 该射门对 OAAI 的变化贡献了多少 | 公式 + 版本化参数 + 重新计算 |
| **Level 3** | Statistical Association（统计关联） | 多场样本下的相关性，需基准与不确定性 | 高位夺回较多的球队，之后射门是否更多 | 样本量、基准比较、置信区间 |
| **Level 4** | Causal Inference（因果推断） | 需明确因果假设、混杂因素与识别策略 | 战术调整是否使进攻效率提高 | 因果图、识别条件、敏感性检验；**不得由事件回溯直接得出** |

**产品规则**：
1. 默认输出只允许 Level 1–2；Level 3 需多场数据与不确定性展示；Level 4 仅在研究模式开放，并显式展示假设与识别策略。
2. 界面上每条论断显示其层级徽章，用户可点击查看证据范围与局限。
3. 措辞随层级变化：Level 1 “记录到……”，Level 2 “按指标计算，贡献为……”，Level 3 “在样本中呈正相关……”，Level 4 “在假设……下，估计效应为……”。

#### 4.2.0.1 `Claim` 数据结构扩展

在现有 Claim 结构上新增以下字段：

| 字段 | 类型 | 含义 |
| :--- | :--- | :--- |
| `claim_level` | enum(1–4) | 推理层级 |
| `evidence_scope` | object | 引用的事件 ID、时间窗口、比赛范围、样本量 |
| `assumptions` | list[str] | 论断成立所依赖的假设（Level 3–4 必填） |
| `counterevidence` | list[ref] | 已检索到的反例或替代解释，空列表需注明“已检索无反例”还是“未检索” |
| `verification_method` | str | 重算脚本、统计检验或因果识别方法的标识 |

#### 4.2.1 势头解释：Momentum 的指标贡献与事件解释（原 C1-5）
- **痛点**：竞品动量图只显示波形，用户不知道曲线为何变化；
- **组件形态**：OAAI 曲线（见 2.2.2）+ 窗口内贡献最大的若干事件列表（Level 2）+ 可点击跳转到对应控球序列；
- **三个子模块**：活动曲线（L-A/L-B）、指标贡献分解、事件解释（Agent 仅可在 Level 1–2 范围内叙述）；
- **边界**：曲线拐点不等于战术原因；若需要“为什么”，只能给出候选解释并走 Alternative Hypothesis Assessment（见 6.4）。

#### 4.2.2 失去球权后的快速球权恢复（原 C1-1，原“6 秒反抢”）
- **定义**：失去球权后 6 秒内本队再次获得球权的**可观察现象**；窗口长度作为参数，需做敏感性分析；
- **不可断言**：没有受压标志或 Tracking，不能确认球队实施了有组织的 Counter-Pressing；
- **展示**：恢复位置、恢复率、恢复后的下一次射门，与对手的反击数据并列展示。

#### 4.2.3 Team Action Density Differential（原 C1-3，原“热区对抗图”）
- **公式（含义修正）**：
  $$\Delta D(x,y)=\frac{D_{\text{home}}(x,y)}{\sum D_{\text{home}}}-\frac{D_{\text{away}}(x,y)}{\sum D_{\text{away}}}$$
  它比较的是**两队事件在各自空间分布中的占比差**，不是严格的“控球率归一化”，也不是对抗强度；
- **边界**：两队热点重叠**不能**证明双方在该区域有高强度身体对抗，原“Friction Zone”命名撤销，改称“双方密度均较高区域”，并在图例注明；
- **口径**：需声明所用事件类型、网格分辨率与是否按有效比赛时间归一化。

#### 4.2.4 What-if Decision Sandbox（原 C2-3，保留并升级为研究方向）
期望效用的一般形式：
$$\mathbb{E}[U\mid a,s]=\sum_{o}P(o\mid a,s)\,U(o,s)$$
其中 $a$ 为假设动作，$s$ 为已知状态，$o$ 为可能结果。若没有接球球员、防守者与无球站位信息，就**不能假装已知** $P(o\mid a,s)$，所以分三个模式：

| 模式 | 回答的问题 | 所需条件 | 输出性质 |
| :--- | :--- | :--- | :--- |
| **Descriptive** | 如果球到达指定区域，位置价值变化多少？ | xT 网格 | 位置价值差（Level 2），不含成功率 |
| **Scenario-based** | 用户设定成功概率与丢球损失，结果如何变化？ | 用户输入假设 + xT | 敏感性展示；概率完全由用户设定并显示 |
| **Research** | 能否训练并验证传球成功率与后续状态价值？ | 多场数据、验证集、校准评测 | 仅在模型通过评测后启用，并展示不确定性 |

早期版本中的“$\Delta xT=+0.17$ 与真实期望 $-0.134$”等示例数值缺少可复核来源，已删除；若后续保留数值案例，须附数据集、程序与结果文件。

#### 4.2.5 其他保留方向（定义同步修正）
- **进攻通道（BL-08）**：明确左右方向、通道分母、事件覆盖率，支持球队对比；
- **球员八轴雷达（BL-07）**：只在同位置、足够样本的标准化比较群体内输出，单场小样本不输出排名百分位；
- **Highlight Locator（BL-12）**：与 OAAI 变化点检测和 S2 序列索引共用底层，输出“候选高光”及其依据层级。

### 6.2 信息架构：共享状态的三个工作空间

> **修订说明**：早期版本把“280px 控制坞 + 中央球场 + 360px Agent 面板”作为整个产品的唯一桌面界面。该布局适合分析工作台的一种状态，但不适合作为全部用户旅程。正式方案改为三个工作空间，共享同一份比赛状态。

#### 6.2.1 三个工作空间

| 工作空间 | 核心视觉 | 用户主要任务 | 典型入口 |
| :--- | :--- | :--- | :--- |
| **Match Center** | 比分与时间线、OAAI 曲线、Shot Map、重点 Insight | 了解比赛发生了什么 | 默认首页、Match Board 选择比赛 |
| **Analysis Explorer** | 大球场、网格、序列、指标、窗口比较、双队密度差 | 深入调查、比较、下钻 | 在 Match Center 点击曲线、事件或区域 |
| **Intelligence Studio** | Agent 观点（含 `claim_level` 徽章）、Hypothesis Lab、Challenge、Evidence、Match Story | 检验解释、制作内容 | 点击论断、发起质疑、导出内容 |

**共享状态**：比赛时间、球队视角、选中事件、选中 Sequence、Snapshot、已审核的 Claim、当前 `metric_versions`。切换空间不重置这些状态。

#### 6.2.2 用户旅程示例
1. 用户在 Match Board 选择一场比赛，进入 Match Center，看到 OAAI 曲线出现明显变化；
2. 点击拐点，进入 Analysis Explorer，看到该窗口贡献最大的若干事件（Level 2）与对应控球序列；
3. 点击某条 Agent 论断，进入 Intelligence Studio，查看其层级、证据范围、假设与反证；
4. 若不同意，发起 Challenge；通过后可把已核验的 Claim 送入 Match Story 与 Graphics Export。

#### 6.2.3 响应式与性能指标
- 桌面端可三栏并列显示，窄屏下三个工作空间改为底部切换；
- 原稿中“100ms 内完成画布切换”“50ms 完成联动”等硬性数值**不再作为算法正确性条件**。改为在真实目标设备上测量交互响应（如点击到画面更新的 P50/P95 延迟），并在验收报告里记录设备、数据规模与测量方法；
- 加载、空状态、错误状态与键盘可访问性需单独验收。

### 6.3 数据管线：隔离的 Schema 与 xT 建模

#### 6.3.1 规范化事件与衍生指标分离

> **修订说明**：早期 `UnifiedEvent` 含 `derived_xt: float = 0.0`，把模型结果混入原始事件字段，且缺失值与真实 0 收益无法区分。正式设计把四类对象隔离（见 3.2.2），并补齐比赛、时钟、方向与来源语义。

```python
class RawSourceRecord(BaseModel):
    provider: str                 # 例如 "statsbomb_open_data" / "synthetic"
    provider_event_id: str
    schema_version: str
    license_ref: str              # 许可与署名条款引用
    payload_ref: str              # 原始 JSON 的存储位置

class NormalizedEvent(BaseModel):        # 只含已观察字段
    event_id: str
    match_id: str
    source: RawSourceRecord
    period: int
    clock_seconds: float                 # 比赛时钟定义见 clock_basis
    clock_basis: Literal["period_elapsed", "match_elapsed"]
    team_id: str
    attack_direction: Literal["left_to_right", "right_to_left"]
    possession_id: Optional[str]         # 来源提供的球权段 ID，若无则 None
    possession_changed: Optional[bool]   # None 表示数据源未提供
    player_id: Optional[str]
    action_type: ActionType
    outcome: Optional[str]
    x: Optional[float]; y: Optional[float]          # 统一米制坐标，None=未记录
    end_x: Optional[float]; end_y: Optional[float]

class DerivedMetric(BaseModel):          # 模型输出，独立存放
    metric_id: str
    event_id: str                        # 指向 NormalizedEvent
    name: Literal["xG", "delta_xT", "oaai_contribution"]
    value: Optional[float]               # None=不可计算，区别于真实 0.0
    status: Literal["ok", "not_applicable", "missing_input"]
    model_version: str
    uncertainty: Optional[dict]
```

要点：
- 缺失值用 `None` 和 `status` 表达，不用 `0.0` 占位；
- 球权变化、攻击方向、时钟定义显式入库，避免接入真实数据时丢失语义；
- 所有 `DerivedMetric` 记录 `model_version`，Claim 引用时一并校验。

#### 6.3.2 StatsBomb Open Data 接入要求
- 数据包含赛事、阵容、事件及部分 360 文件；
- 接入时必须记录并展示其**署名与 Logo 使用要求**，条款以仓库当前 LICENSE / 用户协议原文为准，逐字核对后写入 `license_ref`，不在本文复述条款内容；
- 兼容性测试：字段缺失、同一时刻多事件、点球大战、加时赛、坐标越界、事件类型未映射。

#### 6.3.3 xT 建模
xT 采用独立规范 [`XT_MODELING_SPEC.md`](file:///d:/Projects/match-lens/docs/XT_MODELING_SPEC.md)，要点如下：
- 标准 xT 主要评价**成功保持球权的推进动作**，不是对射门、抢断、犯规都通用的价值评分；
- 支持加载预计算价值网格与自主拟合两条路径，不设“500 场”硬门槛，样本需求由 Bootstrap 稳定性检验经验确定；
- 价值迭代**不涉及矩阵求逆**，早期“单场矩阵稀疏会导致求逆崩溃”的说法已更正；真实问题是小样本下转移概率方差大；
- 早期版本中的“74.5% 零触球网格”“99.6202% 稀疏度”等数值，在补充数据集、程序、随机种子与结果文件之前**不作为已验证结果引用**（相关实验脚本位于 `services/api/tests/test_adversarial_empirical.py`，如需引用须先复核并归档输出）；
- 模型文件须带数据来源、版本与许可信息。

### 6.4 Agent 架构：先分工，再用对照实验证明价值

> **修订说明**：保留第三 Agent 方向，但不再默认它“能发现真实战术因果”。原 `CausalAttributionAgent` 重命名为 **Event Attribution Specialist**，先承担 Event Contribution Analysis 与 Alternative Hypothesis Assessment。同时要区分“新增工具能力”和“新增智能体能力”。

#### 6.4.1 角色与职责

| 角色 | 职责 | 输出层级 | 专用能力 |
| :--- | :--- | :--- | :--- |
| **Analyst** | 提出值得调查的问题与候选解释 | Level 1–2 草案 | 现有事件与指标查询 |
| **Event Attribution Specialist** | 查询序列、分解指标变化、寻找替代解释 | Level 2 为主，Level 3 需多场数据 | **专用工具**：窗口贡献分解、事件链检索、替代候选分析 |
| **Independent Verifier** | 独立核查论断、反证、适用范围与局限 | 为 Claim 填写 `counterevidence`、`assumptions` | 只读证据访问，重新计算 |
| **Deterministic Publication Gate** | 验证数字、事件引用、证据版本与发布条件 | 非 LLM | 规则与重算 |

Event Attribution Specialist 必须拥有真实专用工具，而不是把 Analyst 的文字再读一遍。

#### 6.4.2 对照实验设计
为判断新增收益来自新计算能力还是仅仅多了一次 LLM 调用，比较三种配置：

| 配置 | 描述 | 控制变量 |
| :--- | :--- | :--- |
| **A. 双 Agent** | Analyst + Verifier（现状） | 同一批比赛、同一预算 |
| **B. 双 Agent + 专用工具** | Analyst 与 Verifier 获得窗口贡献分解、事件链检索工具，不新增角色 | 同上 |
| **C. 三 Agent** | 增加 Event Attribution Specialist | 同上 |

评测指标（需由实际运行产出，本文不预设结果）：论断与事件引用的正确率、Gate 拦截率、Verifier 发现的错误数、替代假设覆盖度、专家盲评打分、单场成本与延迟。只有 C 相对 B 显著提升，才说明第三个角色本身有价值。

#### 6.4.3 Publication Gate 2.0
在现有门禁基础上新增检查：
1. 论断的 `claim_level` 与措辞一致；
2. Level 3–4 的 `assumptions`、`verification_method` 非空；
3. 引用的事件与指标 ID、版本存在且匹配；
4. 涉及无球状态时返回 Data Sufficiency 提示（沿用并增强 R2 Evidence Gap Advisor）；
5. 反证检索状态已记录。

#### 6.4.4 Data Sufficiency 提示（示例措辞）
> “当前数据为常规事件流，不包含全体球员的连续位置，因此无法唯一确定防线站位。已为您提供可观察的替代指标：失去球权后的快速球权恢复、对方在该区域的事件密度。”

## 八、结论

本版研究遵循“保留功能、重写论证、重组架构、补齐验证”的原则：

1. **基线**：以 `116f735` 的代码核对为准，R0.1–R2 不重复计入增量；BL-05 属于 R2 Evidence Gap Advisor 的增强，BL-11 属于既有 R3 规划；
2. **推理**：所有论断分为可观察事实、指标归因、统计关联、因果推断四层，并落实到 `Claim` 字段与 Publication Gate；
3. **数据与算法**：无球状态用可辨识性分析界定边界；xT 采用 `XT_MODELING_SPEC.md` 的完整建模与评测协议；OAAI 为自主定义指标，不声称还原竞品；What-if 分三种模式；
4. **架构**：数据采用“覆盖 / 衍生 / 证据质量”三个正交维度与四类隔离对象；界面采用共享状态的三个工作空间；第三 Agent 保留，须通过三配置对照实验证明价值；
5. **规划**：12 项 Backlog 全部保留，以 Track A–E 的依赖关系推进，不再使用无来源的工时估算；
6. **证据纪律**：未附数据集、程序、随机种子与结果文件的具体数字（如幻觉率、稀疏度、授权价格、反事实数值）一律不作为结论引用。

**待补材料清单（后续需实际产出）**
- OAAI 的敏感性与因果滤波测试报告；
- xT/xG 训练与评测结果文件（含数据来源与许可记录）；
- 三配置 Agent 对照实验记录；
- StatsBomb 接入的署名与许可核对记录。
